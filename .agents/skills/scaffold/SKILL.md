# Scaffold

A production's own `AGENTS.md`, `README.md`, and source own its meaning; read them and the installed package APIs before interpreting, authoring, or reviewing it. Repository instructions never override them.

[Scaffold prompting](../scaffold-prompting/SKILL.md) owns the design of shipped task skills, contracts and routers. This skill owns their distribution and production ownership boundaries; [development](../development/SKILL.md) owns implementation changes to the materializer and checker.

- The scaffold owns its production skills, directly linked resources, and contracts, apart from the shared repository items below; its own skills describe making a production, not developing this repository. Read its [production skill](../../../packages/template/scaffold/.agents/skills/production/SKILL.md) for project scope, video generation, editing, encoding and handoff, and [story](../../../packages/template/scaffold/.agents/skills/story/SKILL.md) before changing narrative authoring. Its [source layout](../../../packages/template/scaffold/.agents/skills/development/layout.md) is the backbone of the production: a folder change moves the layout table, the boundary elements in the scaffold `lint.config.ts`, the development stages of `@automovie/evidence` and the contract respondents together, or they disagree about where code belongs. Its task documents preserve the four layers, scripts expression within construction, and screenplay naturalness; independent review, contracts and graph configuration keep their own roles. Installed package APIs own API documentation; the scaffold does not duplicate them. `@automovie/evidence` owns reusable evidence defaults and native graph composition; the scaffold keeps one options object evaluated by native `pnpm evidence`.
- The primary output is a whole deterministic motion-video hint from a complete LLM-authored screenplay: program the main scenes' motion and staging, then assemble the full video. Stills or pilot clips do not complete that commission. The production's [motion skill](../../../packages/template/scaffold/.agents/skills/motion/SKILL.md) owns programmatic choreography, constraints, scene time, and engine feedback; 3D modeling owns its asset representations. Simple representations must accurately carry the intended performance; Human and detailed 3D are optional. Keep separately commissioned screenplay, whole motion hint, finished direct 3D film, and finished post-diffusion film distinct. Direct 3D needs no diffusion, and a motion hint needs no finished diffusion film.
- Default lint and evidence configurations serve ordinary TypeScript development; narrative work opts into its additional workflow while retaining engineering checks. Long-form work preserves settings → treatments → scripts → final screenplay, with construction, expression revision, evidence, current independent review, and whole-work completion. Short video runs settings → final screenplay, and asset-only work has no narrative. Compact questions within those responsibilities rather than removing the architecture.
- An empty `$<name>` file under the scaffold's `.agents/skills` ships the repository item `<name>` at the same place under `.agents/skills`: `$3d-modeling` the whole folder, `development/$repair.md` the single file. The [instruction synchronizer](../../../packages/template/build/syncScaffoldInstructions.ts) copies those items into `lib/skills` on `prepare` and `build`, and the scaffold reader ships them in the placeholders' place. Share a repository skill this way instead of keeping a second copy, and edit it at its repository source under the [prompting](../prompting/SKILL.md) rule for shared skills.
- Untracked files under `scaffold` still ship, so remove stale copies from a checkout before packaging.
- The generated project-root `PROJECT.md` owns adopted production scope, delivery and setup decisions; `docs/instructions` owns creative instructions. Runtime README and `.env.example` own nonsecret operational setup and variable names, ignored `.env` holds actual secrets, and `src/integrations` can hold provider or local-tool code.
- Package upgrades do not rewrite productions. Explicit instruction updates use the CLI sync documented in the [CLI README](../../../packages/cli/README.md), which updates routers and bundled task resources while preserving contracts, project decisions, configuration and authored content. Reusable package implementation stays with its package.
- For an authorized update to an existing production, compare the adopted baseline, proposed scaffold and actual local files before applying its named scope. Preserve project choices and custom contracts; align changed addresses, selected respondents and consumers together. Follow that production's repair rules for affected answers and reviews. Use sync check to inspect changes and conflicts before applying them. New installations retain instruction digests; legacy projects need an explicitly verified prior instruction baseline for differing existing files. Do not infer renewed approval from new wording or overwrite a repaired body with an old working edition. A scaffold edit alone reaches future installations until sync is explicitly run.
- For changed installation behavior, observe a generated project's installed entry point and its `lint`, `evidence`, and `test` commands.
