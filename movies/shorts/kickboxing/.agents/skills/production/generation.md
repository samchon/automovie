# Prepare video requests and acquire takes

Use this branch to prepare requests for a selected generator or acquire commissioned generated video. A complete motion hint and a finished direct 3D film have their own delivery boundaries; neither silently requires an external generator. Read the adopted scope, provider and setup authority in [project context](profile.md), the actual brief or screenplay and any current motion inputs. Use the selected service's existing connector, CLI or API and current documentation; a package that schedules renders supplies no generation service.

## Establish a usable input path

Prepare programmed motion and its aligned controls through [conditioning handoff](conditioning.md). Identify which required scenes the generator will realize and the exact adopted inputs each consumes: motion video, reference image, pose, depth, masks, audio or text as supported. Verify its actual dimensions, frame rate, duration, coordinate or skeleton convention, identity controls and available output contract. A plausible-looking skeleton or a seed does not prove compatibility. Keep the original programmed hint and its identities available for comparison.

Verify the selected model, version and operation in current official documentation, retaining support and limits through [production research](research.md) and linking the adopted setup. Confirm actual video input separately from image-to-video: accepted reference types, counts and roles; per-file and aggregate byte and duration limits; dimensions, aspect, frame rate and codec; upload or transport through URLs, base64, asset IDs or request bodies; incompatible modes; output duration and timing rules. Count all supplied assets and overlaps, not just the main clip. Check whether first/last-frame controls can coexist with the selected reference mode. Distinguish hard limits from recommendations and preserve the stated unit for prompt length, such as characters, words, tokens or bytes. An undocumented limit remains unknown; one provider's current numbers do not define other models. Check the service's actual reference-content restrictions; a generated fictional face is not automatically an accepted upload.

Write the intended scene and reference-role mapping in the production's adopted prompt language, consistent with its actual motion, source identities and local time ranges. State the action, camera and timing to inherit and the appearance or other elements to change, using the service's supported reference labels. Keep a required interaction in the [segment plan](conditioning.md#preserve-and-inspect-the-actual-handoff) rather than expect text to restore a missing contact. Save exact planned text and payload templates through [generation records](generation-records.md), identifying unresolved upload fields and unverified compatibility. Prompt preparation alone requires no generation job; distinguish documented support from a tested submission and generated result.

When generation is commissioned and execution is authorized, prove one representative input, generation, download and playback path before submitting the full batch. Choose a case that exercises the intended performance, required contacts or interactions and any identity continuity the production relies on. Inspect the result against the intended action and the applicable [delivery questions](../contracts/delivery.md); record unsupported controls instead of assuming the model will repair the source motion. Fix input or integration causes before multiplying them across scenes.

## Submit and adopt takes

Use [generation records](generation-records.md) before the first submission and through retries, take selection and media retention. Bind the video request to its actual screenplay action and settings identities, and identify every supplied motion/control/reference input and transformation.

Keep generation outside frame evaluation and deterministic replay. Bind each request to exact input bytes, source revision, provider/model identity, settings, prompt, job identifier and actual result. Inspect the service's existing job state before retrying an uncertain submission; retrying can create another billed job. Keep credentials out of requests saved as provenance. Apply the production's adopted cost and operating limits rather than silently changing quality, provider or scope.

Retain downloaded outputs and necessary sidecars in project-owned fixed assets with their content digests, source relationships and usage terms. A transient URL, seed or completed job is not the accepted take. Preserve originals separately from conversions, trims, retiming or other derivatives, and identify the exact take the actual consumer uses. Use supported decoding and delivery paths; add only the integration the production needs through [development](../development/SKILL.md).

Inspect every candidate take before adoption, collecting the batch's observed causes and retained achievements before correction. A retry is a new candidate with its own identity. If a result loses required action, identity or causality, repair the source, request or take selection at its owner and inspect the affected neighbors; a cut cannot substitute for the missing performance.

## Hand accepted media to the edit

Measure the accepted files' actual duration and timing. Hand accepted takes and their source relationships to [editing and finishing](finishing.md), with original motion timing, required action and sound boundaries, and unresolved limits. Reconcile generated performance with captions, speech, reactions and adjacent shots rather than assuming the request duration was returned. A generated clip is not the complete film; [delivery review](../review/delivery.md) judges the actual assembled output.
