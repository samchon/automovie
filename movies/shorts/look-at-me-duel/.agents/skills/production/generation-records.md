# Record generation requests and retain media

Use this guide when preparing requests or using image, mesh, speech, music, sound or video generation, including video-to-video. The next author must be able to explain the request's purpose and status, recover its actual inputs and locate any result. A prompt and seed do not preserve nondeterministic output bytes.

## Own the request

Before generating, inspect available production or shared-library assets and their request/source records. Reuse an existing compatible character identity, voice, object or other input rather than regenerate the same subject for each consumer. Give the shared asset and its request one canonical owner; each consuming production records the adopted scope, local variants, actual retained locator and use. Different ages, proportions, costume, hair or scene states remain owned by their local settings or screenplay; an identity reference does not silently replace them. Generate a new variant only for a required difference or an observed incompatibility, documenting that cause and its relationship to the existing asset.

Before submitting, create a tracked Markdown record at `docs/prompts/<purpose>/<descriptive-name>.md`. Use plural purpose folders such as `images`, `voices`, `sounds`, `videos` or `models`. Name the subject and intent so another author can recognize the request without opening it: `voices/carina-quidditch-taunt.md`, `images/carina-character-reference.md` or `videos/quidditch-broom-transfer.md`. A coherent batch can use a name such as `voices/quidditch-dialogues.md`, with meaningful stable H2 identities for distinct requests or attempts. Keep provider request/job/attempt IDs in the record's metadata; ID-only, UUID-only or ordinal-only filenames do not describe the content. Meaningful titles can include version, shot or take numbers, such as `carina-taunt-take-2.md`. Record its purpose, target asset/shot/dialogue, intended consumer and current status. A planned request is not an executed job. Create only records the work needs; an empty production has no generation population.

Keep the exact submitted text and nonsecret request fields, including positive, negative, role/system text and structured parameters only where actually supplied. Preserve spelling, punctuation, order and line breaks that the receiver consumed. A linked tracked payload can own large structured text; identify its digest rather than maintain a conflicting copy. Distinguish the observable connector/CLI request from an unobserved provider payload or internal prompt rewrite. State unsupported, omitted and unknown fields honestly.

For commissioned prompt preparation, retain the exact planned text and nonsecret payload template even when no job is authorized. Mark unresolved upload URLs, asset IDs and other runtime fields explicitly, and distinguish planned references from files already supplied. Keep the submitted request as a separate attributable attempt if execution later occurs; a template with placeholders is not that request.

Identify provider/tool and version, model/checkpoint revision, operation, relevant settings and seed or its absence/support limit. Preserve the nonsecret executable command or API payload and selected runtime/configuration identity. Reference existing receipts as their single owner instead of copying parameter values into several records. Credentials, authorization headers and secret-bearing URLs stay outside tracked records.

## Bind each instruction to its source

For the appearance, voice, words, action, composition and timing the request constrains, identify the actual source file and stable H2, shot, paragraph, line or time span. Record the exact source revision or content digest actually read, its digest convention, and a short literal excerpt or precise value. Explain which request field or instruction each source supports and any deliberate transformation, omission or unresolved conflict. A directory link, a character name or an entire screenplay hash without a usable locator does not establish this relationship.

Settings supplies identity and baseline world facts; screenplay supplies performed words, action, access and results. An asset-only request uses its actual brief or reference. Distinguish inherited facts, adopted external references, user choices and new delegated production choices. A newly chosen incidental detail can be owned in the request record with its reason; a changed canonical value returns to its creative owner. Do not invent a settings or screenplay ancestor for an independent technical probe.

Use explicit source links, identities and mapping prose or tables in the record. Configure native Evidence relationships only where the actual respondent and installed API can express them; otherwise independent source/asset/delivery review checks these exact bindings. A comment without that trace is not proof, and unconfigured `@evidence` tags create no coverage. This requirement adds no narrative stage and grants no approval to a source or result.

## Identify input bytes and attempts

For every supplied image, recording, motion video, pose/depth/mask pass or other reference, record its role, retained locator, content digest, size and necessary format facts. Link its source record and usage rights. Capture crops, conversions, clip ranges, frame/time mappings and sidecars that the receiver actually consumed; distinguish time-matched controls from unpaired identity references. A thumbnail or URL does not identify the full submitted bytes. Dependencies needed for restoration follow the same retention rule as the generated result.

For each video segment, link its meaningful request identity to the exact retained clip and whole hint, source revision and screenplay action locator. Record measured local/global time and included frame ranges, duration, dimensions, frame rate or time base, codec, bytes and digests, with any overlap or continuity references and their roles. Planned ranges remain planned until the actual export establishes them. Link the selected model/mode's documented budget and actual request totals instead of treating an output duration cap as the input allowance.

Before retrying an uncertain submission, inspect the existing job. Record request/job identifiers when available, attempt status, failures and available responses. Preserve the actual request for every retry or edited prompt; do not replace an earlier attempt with the successful version. After a restart, resume from the last verified job or retained file, marking unavailable provider state rather than inventing success.

For older work, label a record reconstructed after generation and name the commands, payloads, logs or receipts used. Separate a historical source identity actually recorded from a present-day source correspondence checked later. An unknown original source revision remains unknown; a current hash is not evidence that the generator used that version. Do not create fictional image/video runs to fill a record tree.

## Register results and their use

After the call, identify each actual original output by retained locator, digest, byte size and relevant image/audio/video/mesh format and timing facts. Link the request attempt, source dependencies, licensing/attribution and actual observations. Distinguish generated candidates, rejected takes, adopted inputs and delivered media, with the selection reason and remaining checks. Successful generation or a waveform is not visual, listening or transcript acceptance.

Keep original outputs distinct from trims, retiming, resampling, conversions and other derivatives. Identify their source/output digests and transformations, then link the exact bytes and time range used by the real asset, shot, measurement or edit consumer. A prompt record alone cannot prove that those bytes entered the film. Recheck affected source bindings and consumers when creative sources, request fields, references, media or the edit change; preserve earlier attempts and their attributable observations.

## Keep small records in Git and large bytes retrievable

Track prompts, source mappings, nonsecret payloads, receipts and concise measurements. The scaffold ignores `/media/generated/` for large generated bytes; use it when no existing project-owned media location is adopted. Keep runtime public paths and existing storage arrangements explicit in README and asset records. Ignore only adopted generated-media paths, not every image/audio/video extension across fixtures, documentation and source. Git ignore affects tracking, not retention or runtime access, and does not untrack already committed files.

When an exact submitted input list, payload or raw source snapshot must survive byte-for-byte, verify that Git attributes and filters preserve it on storage and checkout. Line-ending conversion can invalidate a raw digest even for a small text file. Use a narrowly scoped byte-preserving attribute or verified encoding for those immutable inputs, record the digest convention, and check the round trip without changing the original bytes. Ordinary editable documents do not justify disabling text normalization across the repository.

The default renderer's `/output/` exports are also ignored. Preserve the nonsecret capture receipt or its sufficient measurements in tracked `docs/analysis/`, with the original report/output identities and retained locators. A deterministic render uses its actual source/configuration provenance; do not invent a generation prompt for a renderer that submitted none.

Each required input, adopted take and delivery output needs an availability state and a usable retained locator. State whether it is locally retained, durably archived and verified, unavailable, or deliberately disposed. Local ignored storage remains a dependency that another checkout must obtain; record the restoration command or procedure, access requirement without credentials, and digest verification. A transient service URL or promised future backup is not a durable archive. Keep the currently used bytes and necessary source references until their declared retention obligation is met.

Delete task-owned disposable intermediates only after checking that no current consumer or review needs them. Before deleting required local media after archival, restore the archived bytes through the documented path and verify their digests and dependency completeness; retain that result and the availability change. A rejected take may be disposed under the adopted policy while its request, rejection reason and output identity remain recorded. If bytes are missing, report the loss and affected acceptance/reproducibility limits. Regeneration is a new candidate, even with the same prompt and seed.

## Review the actual chain

At acquisition and handoff, compare the complete request population with its actual sources, inputs, attempts, outputs and consumers under [asset](../contracts/assets.md) and [delivery](../contracts/delivery.md) questions. Open retained inputs/results and verify their identities and availability to the extent the commission needs. Explain which source relationships received native coverage and which were checked by inspection. Instruction consistency, a passing graph and a faithful request do not establish generated quality or a delivered film.
